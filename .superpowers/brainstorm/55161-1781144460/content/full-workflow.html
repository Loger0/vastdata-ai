完整工作流 — Framework Analyzer 前置

两种集成模式的分支处理

🆕 Framework Analyzer 内部流程

Step 1
获取框架源码 — 根据 Issue 提供的上游 URL，克隆到分析目录
Step 2
诊断集成模式 — 分析目录结构/模块组织，判断：独立包 还是 原生集成
Step 3
分析耦合度 — 找到向量数据库相关的抽象接口/注册机制/配置入口，列出需修改的文件清单
Step 4
评估测试基础 — 搜索测试目录/CI 配置，判断：有官方测试 / 部分覆盖 / 完全缺失
Step 5
产出 Framework Profile — JSON 格式标注到 Parent Issue，驱动下游分支
路径 A：独立包模式（LangChain / LlamaIndex）
📋 Profile: 集成=独立包, 耦合=低, 测试=有, 修改文件=0
🟢 代码仓库
Adapter 仓库 → 独立开发
🔵 convention-extractor
提取框架接口规范
🔵 test-scout
提取框架官方测试
🔵 eco-issue-splitter
按接口方法拆分子任务
🔵 adapter-dev → code-reviewer → test-adapter
路径 B：原生集成模式（RAGFlow）
📋 Profile: 集成=原生集成, 耦合=中高, 测试=无, 修改文件=3-5
🟠 代码仓库
Fork RAGFlow → 在 fork 上直接修改源码
🔵 convention-extractor
提取参照后端的代码规范 + 项目整体风格
🆕 test-strategist
无官方测试 → 规划 API 端到端集成测试方案
🔵 eco-issue-splitter
拆分为：后端实现 + 配置修改 + 集成测试 子任务
🔵 adapter-dev → code-reviewer → test-adapter （每个子任务的 test-adapter 执行自建测试）

代码仓库策略

集成模式 代码放在哪 仓库操作
独立包 adapter Git 仓库（如 llama-index-vector-stores-vastbase） 在 adapter 仓库上开发，框架源码只读分析
原生集成 Fork 目标框架仓库（如 infiniflow/ragflow） Fork → 在 fork 上创建 feature 分支 → 直接修改源码

测试策略分支

测试基础 test-scout 策略 test-adapter 策略
✅ 有官方测试 提取 + 适配为 Vastbase 版本 单元 + pyvastbase 集成 + 框架官方 + 框架集成（4层）
❌ 无测试 切换为 test-strategist：分析框架 API → 规划集成测试方案 自建 API 端到端集成测试（全流程 demo）
