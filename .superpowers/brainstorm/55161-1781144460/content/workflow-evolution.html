Multica 工作流演进 — 新增框架前置分析阶段

对比：当前 v5 流程 vs 新增 Framework Analyzer 后的流程

❌ 当前 v5 工作流（假设前提不成立）
🟢 Parent Issue 创建（人工填写框架信息）
⬇
🔵 eco-issue-analyst（需求分析）
⬇
🔵 convention-extractor（提取编码规范）
⬇
🔵 test-scout（查找框架测试）
⬇
🔵 eco-issue-splitter（拆分任务）
⬇
🔵 adapter-dev → code-reviewer → test-adapter
⚠ 隐含假设：
· 框架有清晰的抽象接口
· 适配是独立包
· 框架有官方测试
· 耦合度低，不用改目标源码
✅ 新流程：Framework Analyzer 前置
🟢 Parent Issue 创建
⬇
🆕 Framework Analyzer（框架前置诊断）
⬇
📋 产出：Framework Profile
🏗️ 集成模式
独立包 / 原生集成 / 插件
🔗 耦合度
接口抽象 / 需改配置 / 深度耦合
🧪 测试基础
有官方测试 / 部分有 / 完全缺失
📝 需修改文件清单
⬇ 标注到 Issue，下游 Agent 自动适配策略
🔵 eco-issue-analyst
根据 Profile 切换分析模式
🔵 convention-extractor
根据集成模式调整规范提取策略
🔵 test-scout / test-strategist
有测试→提取 / 无测试→规划测试方案
🔵 后续 Agent 链自动适配

Framework Analyzer 诊断输出：Framework Profile

诊断维度 LangChain / LlamaIndex RAGFlow
集成模式 独立包 原生集成
耦合度 低 — 实现抽象接口即可 中高 — 需修改配置/注册/路由等文件
需修改的目标文件 0 个 ~3-5 个（settings, factory, constants 等）
测试基础 框架有官方测试 完全缺失
测试策略 提取官方测试 + 扩充 全自建：API 端到端集成测试
编码规范来源 框架 VectorStore 接口规范 参照现有后端实现 + 项目整体风格
