Framework Profile 输出格式 & Agent 变更清单

Profile 是连接上游诊断和下游实现的契约

Framework Profile JSON Schema

{ "framework": "ragflow", "version": "0.18.0", "source_repo": "https://github.com/infiniflow/ragflow", // ── 集成模式诊断 ── "integration_mode": "native", // "standalone" | "native" | "plugin" "adapter_repo": null, // standalone 模式：adapter git repo URL "fork_target": "infiniflow/ragflow", // native 模式：需 fork 的目标仓库 // ── 耦合度分析 ── "coupling_level": "medium", // "low" | "medium" | "high" "files_to_modify": [ "api/settings.py", "rag/utils/constants.py", "rag/nlp/__init__.py" ], "files_to_create": [ "rag/nlp/vastbase_impl.py" ], // ── 接口抽象分析 ── "abstraction_type": "class_inheritance", // "abstract_class" | "protocol" | "duck_typing" | "none" "base_class": "rag.nlp.abstract.VectorDB", "reference_backend": "rag.nlp.infinity_impl", // 最接近 Vastbase 的参照实现 "required_methods": [ "search", "insert", "delete", "create" ], // ── 测试基础评估 ── "test_infrastructure": "none", // "full" | "partial" | "none" "test_directory": null, "test_strategy": "self_build_e2e", // "extract_official" | "extend_partial" | "self_build_e2e" // ── Demo 规划 ── "demo": { "type": "api_e2e_pipeline", // 由 Analyzer 根据框架用途诊断 "scenarios": [ "knowledge_base_create", "document_ingest_and_parse", "vector_retrieval", "hybrid_search_recall", "knowledge_base_cleanup" ], "validation_criteria": "召回结果与预期一致；过滤条件下结果数量正确" }, // ── 编码规范引用 ── "convention_references": [ "rag/nlp/infinity_impl.py", "rag/nlp/elasticsearch_impl.py" ] }

下游 Agent 变更清单

Agent 当前行为 变更
🆕 Framework Analyzer 不存在 新增 Agent：克隆源码 → 诊断 → 产出 Profile JSON → 标注到 Issue
eco-issue-analyst 假设独立包模式做需求分析 读取 Profile，根据 integration_mode 切换分析策略
native 模式：分析需修改的文件 + 参照后端逻辑
standalone 模式：维持现有逻辑
convention-extractor 从框架接口提取编码规范 读取 Profile，根据 integration_mode 切换提取来源
native 模式：分析 reference_backend + 项目整体风格
standalone 模式：维持现有逻辑
test-scout 查找框架官方测试 读取 Profile，根据 test_infrastructure 切换角色：
· "full" → 提取官方测试（现有逻辑）
· "none" → 切换为 test-strategist：基于 Profile 的 demo.scenarios 规划集成测试方案
eco-issue-splitter 按接口方法拆分子任务 读取 Profile
native 模式：拆分时包含 "修改配置/注册文件" 子任务
standalone 模式：维持现有逻辑
adapter-dev 独立包 TDD 开发 读取 Profile
native 模式：在 fork 仓库上开发，Step A4.5 增加 "读取需修改文件清单"
standalone 模式：维持现有逻辑
test-adapter 4 层测试 升级为 5 层测试，Flow C 增加第 5 层
读取 Profile 的 demo 字段：按 demo.scenarios 编写 Demo
读取 test_strategy："self_build_e2e" 时跳过提取官方测试

设计要点

  • Profile JSON 是唯一真相源，所有下游 Agent 读取同一份
  • Agent 不猜测框架特征，全部由 Analyzer 诊断
  • 每个 Agent 只需要判断 integration_mode 等关键字段即可分流
